## 1. 系统配置 `/system/configs`

### 1.1 配置项与生效语义（五列表）

后端 `system_configs` 表预置以下配置项。**生效语义逐键标注**，不做统一「立即生效」承诺：

| 配置键 | 范围（说明） | 单位 | 读取时机 | 是否影响存量 |
|--------|--------------|------|----------|--------------|
| `gps_checkin_radius_m` | 打卡围栏半径 | 米 | 打卡校验时读取 | 仅影响后续打卡 |
| `order_payment_timeout_hour` | 订单待支付超时 | 小时 | 业务发生时（订单创建）写入截止时间 | **不重算存量订单行** |
| `service_payment_timeout_hour` | 需求待支付超时 | 小时 | 业务发生时（需求创建）写入截止时间 | **不重算存量需求行** |
| `auto_accept_hours` | 自动验收时间 | 小时 | 业务发生时（订单进入待验收）写入 | **不重算存量订单行** |
| `refund_opponent_timeout_hours` | 退款对手处理超时 | 小时 | 业务发生时（退款发起）写入 | **不重算存量退款行** |
| `review_timeout_days` | 评价超时 | 天 | 业务发生时（订单完成）写入 | **不重算存量订单行** |
| `settlement_delay_hours` | 结算延迟 | 小时 | 结算业务触发时读取 | 影响随后触发的结算 |
| `credit_score_initial` | 信用分初始值 | 分 | 新用户注册时 | ⚠️ **`credit_score_initial` 配置待修复（后端任务 #9），当前实际生效值 600**（注册代码硬编码，与配置不一致）；修复前改配置不改变新用户初始分 |
| `credit_score_max` | 信用分上限 | 分 | 信用分变动校验时（部分路径读取配置） | 不重算历史信用分 |
| `credit_score_min` | 信用分下限 | 分 | 信用分变动校验时（部分路径读取配置） | 不重算历史信用分 |

> **超时类配置的共同语义**：在业务发生时写入对应行的截止时间，**修改配置不会重算已存在的存量行**；编辑弹窗中如实提示该语义，不承诺「立即生效于所有业务」。
> **信用分边界缺口**：部分路径（如管理员手工调整）硬编码 0~1000，与配置读取不一致（⏳ 后端任务单 #9）。

### 1.2 编辑

- 点击某一行的「编辑」，弹出内联编辑或弹窗
- 修改后调用 `PUT /api/v1/admin/system-configs/:key`，Body：`{ "value": "24" }`（**value 为字符串**，数字也以字符串提交）
- **二次确认**：确认文案按 §1.1 五列表的该键语义展示（如「将影响随后发生的业务，存量订单不受影响」），不使用统一「立即生效」话术

### 1.3 交互约定

- 数值类型校验：只允许数字，信用分相关需在配置边界内
- 不可删除配置项（配置项由后端种子数据初始化）
- 配置变更记录到 `admin_audit_logs`（后端自动处理；**系统配置接口当前不接收独立 reason**，前端**不展示「填写原因」输入框**，⏳ 任务单 #9 后再评估）

## 2. 信用分规则 `/system/credit-rules`

### 2.1 规则列表

后端 `behavior_rules` 表存储信用分规则，运营可调整分值，无需发版。

| 列 | 说明 |
|----|------|
| 行为键 | G-1~G-10（加分）/ B-1~B-10（扣分） |
| 行为名称 | 如「完成订单」「爽约」 |
| 分值 | 正数为加分，负数为扣分 |
| 启用 | 状态展示 |
| 更新时间 | |

### 2.2 编辑（统一流程，无即时保存）

**「开关即时保存」已删除**，统一为：编辑 → 二次确认 → 保存。

- 行内「编辑」进入编辑态（分值输入 + 启用开关），点击「保存」弹出二次确认，确认后提交
- 取消则还原，不做任何请求
- 接口：`PUT /api/v1/admin/credit-rules/:id`，Body：`{ "delta": 10, "isActive": true }`（**camelCase**）

**⚠️ 两个独立校验域（S06 冻结，不得混用）**：

| 校验域 | 含义 | 取值范围 | 说明 |
|--------|------|---------|------|
| **规则 `delta`（本次编辑的字段）** | 单次行为的信用分增减量 | **整数 -1000 ~ 1000**（后端 `admin_validate.go` 对 `BehaviorRule.Delta` 的现状校验） | **允许负值**（扣分规则如 `-50` 是合法配置）；0 也合法 |
| **`credit_score_max` / `credit_score_min`（系统配置）** | 用户信用分**总分**的上下边界 | 由 §1 配置项单独定义与修改 | 约束的是用户累计总分落点，**不是**单次增减量；修改总分边界**不会**（也不应）屏蔽负分规则 |

> 编辑弹窗对 delta 的校验为「整数 -1000~1000」，不得按 `credit_score_min/max` 配置值动态收紧——否则默认 0~1000 边界会**禁止所有扣分规则**。两域在 UI 上分开定义、分开展示。
> 管理员手工调整用户信用分路径的硬编码缺口（0~1000）已登记 ⏳ 任务单 #9，与本节规则编辑校验无关。
- 信用规则接口当前不接收独立 reason，编辑确认弹窗**不展示「填写原因」框**（⏳ 任务单 #9 后再评估）

### 2.3 规则说明（只读展示）

在列表上方展示信用分机制说明（数值取自系统配置，不硬编码）：

- 初始值 / 上限 / 下限：读取 `credit_score_initial` / `credit_score_max` / `credit_score_min` 配置展示
  - ⚠️ **初始分说明区必须标注**：「`credit_score_initial` 配置待修复（后端任务 #9），当前实际生效值 600」——不得把配置值展示为已生效的新用户初始分
- 加分行为：完成订单、好评、连续无差评、实名认证、资质认证、签到、邀请好友等
- 扣分行为：爽约、取消订单、迟到早退、差评、围栏外打卡、退款纠纷、违规被下架、举报成立等

> 规则分值调整影响后续触发的行为，历史信用分不受影响。

## 3. 服务费配置 `/system/fee-config`

> 后端 `fee_config` 表已存在，接口已实现（分支 `codex/password-login-fee-config`，提交 `7afb63c`）。
> 权限：仅 super_admin。

### 3.1 字段（snake_case 例外）

| 字段 | 说明 | 默认值 |
|------|------|--------|
| 服务费比例 (`fee_rate`) | 百分比 0~100，5 表示 5% | 5% |
| 最低服务费 (`min_fee`) | 金额 ≥ 0，**上限 9999999999.99** | 0 |
| 服务费承担方 (`payer`) | `provider` / `employer` / `split` | provider |
| **雇主承担百分比**（`split_ratio`） | **UI 直接展示并输入「雇主承担百分比」**，0~100%；提交换算 `split_ratio = 雇主百分比 / 100`（雇主 30% → `"0.30"`） | — |

> **不做「服务者百分比」展示与换算**（旧文档的服务者百分比换算描述已作废），从源头消除换算歧义。
> 当 `payer ≠ split` 时，`split_ratio` 为 null，输入框禁用并清空。

### 3.2 输入精度冻结（S09，首期冻结）与换算规则

**首期精度冻结**（后端 `admin_fee.go` 只接受最多两位小数的普通十进制字符串，UI 输入约束与之对齐）：

1. **雇主承担百分比：0~100 的整数步进**（UI 侧约束，步进 1）——**`30.5%` 这类小数百分比前端明确拒绝**（输入框校验直接报错），**禁止静默四舍五入**（资金分摊不允许静默改值）。示例：`30` ✅ → 提交 `"0.30"`；`30.5` ❌ 前端拦截
2. **所有提交值（`fee_rate` / `min_fee` / `split_ratio`）最多两位小数**，超出两位小数的输入前端拦截
3. **`min_fee` 上限 9999999999.99**（后端校验上限，前端同步拦截）
4. **禁止科学计数法输入**（如 `1e-2`）——前端输入框拒绝非常规十进制字符串
5. 金额一律**十进制字符串**提交，换算用 **decimal** 计算，禁止 float

> 若未来需要小数百分比（如 30.5%），须**另立后端精度变更任务**（首期不做）——`30.5%` 换算为 `0.305` 会被后端拒绝，前端不做静默四舍五入兜底。

提交换算：`split_ratio = 雇主百分比 / 100`，示例：雇主 30% → `"0.30"`（十进制字符串）

**计费示例**（页面帮助文案）：价款 100.00、费率 5%、雇主承担 30%：

| 项目 | 金额 |
|------|------|
| 服务费 | 5.00 |
| 雇主承担（30%） | 1.50 |
| 服务者承担（70%） | 3.50 |
| **雇主实付** | **101.50** |
| **服务者结算** | **96.50** |

### 3.3 生效范围（如实标注）

- 修改后**影响随后读取当前配置的业务**
- **已预付需求后续产生的订单仍使用原费率快照**（需求预付时冻结费率）

### 3.4 交互

- 仅允许一行生效（后端唯一索引约束）
- payer 切换为非 split 时，雇主承担百分比输入框禁用并清空
- **百分比输入为整数步进（0~100），`30.5` 等小数输入前端明确报错、不静默四舍五入**（见 §3.2 精度冻结）
- 修改需二次确认，确认文案包含 §3.3 生效范围说明

## 4. 安全要求

1. 所有操作二次确认（确认文案按各节生效语义展示）
2. 修改后 toast 提示「已更新」（**不承诺「立即生效」**，生效语义见 §1.1 / §3.3）
3. 操作日志自动记录（后端 `admin_audit_logs`）
4. 「变更前预览」：弹窗显示旧值 → 新值，确认后提交
