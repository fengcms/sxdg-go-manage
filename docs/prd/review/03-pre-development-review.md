## 一、结论

**有条件通过，可启动项目基础设施及契约明确的页面；尚不能把全部 v2 文档作为无歧义的冻结开发合同。**

本轮共发现 **10 项剩余问题：5 项 P1、5 项 P2**。P1 应在对应模块开发前修订或明确后端任务，P2 应在相关页面验收前收敛；没有发现阻止整个项目启动的技术栈矛盾。

本次修订方向合理：纯内存会话、业务码与 HTTP 状态分离、权限矩阵、真实分页、首期筛选收缩、退款固定动作、雇主分摊比例、上传依赖、审计兼容和分阶段验收均有实质改进。已明确标为待补的接口不再重复判为“规划假定已实现”。但“产品接受方案”“文档修订完成”“后端实现完成”需要分别记录。

## 三、剩余问题

### S01 · P1：用户 JSON 示例及分类构树键仍使用数据库命名

**位置**：`modules/02-user-management.md` §4、`modules/03-content-management.md` §1.3；`api-integration.md` §0.3。

用户响应示例仍是 `avatar_url/is_employer/is_provider/is_admin/credit_score/created_at`，实际 `internal/model/users.go` 返回 `avatarUrl/isEmployer/isProvider/isAdmin/creditScore/createdAt`。分类要求按 `parent_id` 构树，实际 `internal/model/categories.go` 返回 `parentId`。照示例开发会造成空列或无法正确关联节点。

“fee-config 是唯一 snake_case 例外”“数据库字段不出现在 JSON 中”也不成立：同文档看板已列出 `service_gmv/active_users/new_users/available_balance/frozen_balance`；JSON 快照内部还有独立协议。

**建议**：修正具体示例和构树键；将命名约定改为“逐接口 DTO 为准”，明确看板、fee-config、快照等例外，保留禁止全局自动转换的约定。

**验收**：用实际用户/分类响应作为 fixture，验证头像、角色、信用分和完整三级树；看板适配器按其真实键读取。

### S02 · P1：panel 不是合法字段 type，示例必填单选没有可选值

**位置**：`modules/03-content-management.md` §3.3；`api-integration.md` §5。

`internal/service/admin_validate.go:validateTemplateResource` 只允许 `single/multi/tags/drawer/wheel`；`internal/service/form.go` 中 `panel` 是 drawer/wheel 字段的嵌套属性，不是第六种 type。按文档创建 `type: "panel"` 会被拒绝。

当前示例 `area` 是必填 single 却没有 options；模板保存校验可能通过，但 `ValidateForm` 会拒绝所有非空选择，空值又不满足 required，无法完成发布。

**建议**：删除 panel 类型行，补充 `panel.mode/options/groups/wheels` 的结构和对应提交值示例。提供包含 templateName、categoryId、blocks 的完整可用创建示例，单选必须含合法 options；明确“模板保存成功”不等于“发布表单可提交”。

**验收**：示例完成“创建模板→预览选择→提交服务/需求”；覆盖 single、multi、tags、自定义标签上限和 drawer/wheel 的递归结构。

### S03 · P1：交易首期仍要求展示单行响应没有的数据

**位置**：`modules/04-order-refund.md` §1.2、§2.3–2.4、§3.2–3.3、§4.2。

`internal/service/admin.go:AdminRead` 返回单行模型，不做关联聚合。`internal/model/orders.go` 有 employerId/providerId、amount、serviceFee，但没有双方头像昵称或独立“服务者结算”字段。文档要求展示“订单快照中的结算字段”，该字段实际不存在，不能由前端猜值或按当前费率推导。

`internal/model/refunds.go` 没有关联订单号/金额、申请人昵称头像和完整处理时间线。退款来源还包括需求流拍（sourceType=1），不能一律按 sourceId 链接到订单。服务详情的可服务时段等也不在普通单行模型内。“以后端返回为准”不足以说明缺失字段的首期呈现方式。

**建议**：逐列标明来源；首期已有字段直接展示，关联人仅展示 ID/链接，退款按来源类型导航，处理时间线和结算金额无数据则移除。确需保留的展示项列入明确的聚合 DTO 任务，补充结算状态/金额的语义；不要重新引入逐行 N+1 请求。

**验收**：订单、订单退款、需求流拍退款各一条真实响应，页面不出现虚构金额、错误跳转或从不存在字段推导的历史事件。

### S04 · P1：客服只读首期的授权、身份查询与数据来源尚未闭合

**位置**：`modules/05-customer-service.md` §0、§1.3、§2；`api-integration.md` §9；后端任务 #6a。

1. `internal/handler/admin.go:adminRead` 仅对非 super_admin 加当前客服过滤；super_admin 默认拿到全部 cs 会话。`service.Conversation` 对读取消息仍严格校验参与方，因此“我的接待会话+点击查看历史”对超级管理员不能直接成立。应区分列表管理权、转接权和消息阅读权，不扩大消息豁免。
2. #6a 提到“当前客服身份查询”，但没有路径、响应、角色范围及未绑定 agent 的错误/空态定义。普通客服看不到仅 super_admin 可读的 agents 列表，缺少此契约就不能可靠取得自己的 agent ID 切在线状态。
3. 会话列表实际是 `model.Conversation`，只有用户 ID 等字段，没有用户头像昵称；搜索会话也没有冻结的服务端参数。原型仍显示搜索、头像昵称和订单号，需删减或明确摘要 DTO。
4. `ConversationMessages` 只读取本地 chat_messages。现有本地写入包括系统卡片及活动文本，未见普通客服文本/图片的通用落库或腾讯 IM 历史同步链路。不能将这一路径承诺为完整腾讯 IM 聊天记录。

**建议**：#6a 冻结当前 agent 查询及 DTO；超级管理员明确只看本人参与消息，非参与会话不发消息读取请求；首期历史标为“已入库消息记录”，完整 IM 历史随 #6b；删除无接口搜索，或补会话摘要接口。

**验收**：未绑定客服、两名客服、超级管理员分别验证；转接后旧客服立即停止请求并清除当前时间线，新客服可读，非参与管理员不获得消息；明确普通 IM 文本在首期是否可见。

### S05 · P1：封禁字段尚缺失时，封禁/解封按钮仍没有可执行规则

**位置**：`modules/02-user-management.md` §1.2–1.3、§2；`development-plan.md` §4.1；后端任务 #3/#4。

文档仅隐藏缺失的状态列，仍保留“封禁或解封”操作，却无法决定当前按钮。任务 #4 明确详情 banned 字段为 P0，但开发计划把 #4 整项列为二期，详情还错误地仅引用 #3。

**建议**：将 #3a 列表 banned、#4a 详情 banned 独立列为首期依赖。字段未就绪或缺失时状态为“未知”，两个状态切换入口均禁用；不得把 undefined 当 false。解封也说明 reason 来源，保证与权限文档“原因必填”一致。

**验收**：已封禁、未封禁、缺失字段、提交失败四种场景；操作成功重新获取服务端状态，不靠本地猜测。

### S06 · P2：信用规则 delta 与用户信用分上下限混为一个校验范围

**位置**：`modules/06-system-config.md` §2.2–2.3；后端任务 #9。

规则 delta 是单次增减，credit_score_min/max 是用户总分边界。若照“规则边界按配置”直接使用默认 0～1000，就会禁止负分规则。实际 `admin_validate.go` 对 BehaviorRule.Delta 校验为 -1000～1000；#9 目前只明确改管理员手工调整路径，没有定义规则 delta 的新限制。

**建议**：首期明确 delta 为整数 -1000～1000，保留负值；总分上下限与 delta 范围分别定义。初始分配置修复前，说明区不能把配置值显示为已经生效的新用户初始分，应标出当前实际值/待修复状态。

**验收**：-50、0、+50 可保存，越界拒绝；修改总分边界不会无意屏蔽扣分规则。

### S07 · P2：审计日志“没有 IP”的断言和信用分 diff 示例不准确

**位置**：`modules/07-audit-log.md` §1.2、§1.3、§4。

`internal/model/admin_audit_logs.go` 明确返回 `ip`（可空）；第一轮采样文件也包含这个键。可以产品决定不展示 IP，但不能声明后端没有该字段。信用分示例仍使用 before/after.credit_score，实际动作日志可能 before=null、after 为 delta/reason 等动作输入，而非调整后的用户模型。

**建议**：IP 改为可选展示或明确“首期不展示”；示例采用实际动作结构，不把请求增量误标为最终信用分。保留通用 JSON 与未知值回退策略。

**验收**：带 IP、IP=null、before=null、字符串配置 diff 和 delta 动作均正确渲染，不制造不存在的旧分/新分。

### S08 · P2：活跃用户文案仍可能被理解成登录次数或完整登录统计

**位置**：`modules/01-dashboard.md` §2、§4、§7；`api-integration.md` §2。

`admin_dashboard.go` 统计的是 last_login_at 在最近 24h 的**用户行数**，不是登录事件次数；用户日期序列则是“该注册日期用户群中的近期活跃人数”。示例同一组 new_users=23、active_users=345 不可能由此 SQL 产生。

另外 `internal/service/password.go:Login` 不更新 last_login_at，当前密码登录不计入这个指标。这是现有实现缺口，应登记而非宣称已覆盖全部登录方式。

**建议**：文案写“按已记录 last_login_at 统计的近 24 小时登录用户数”；注册日期表写明用户群口径，修正例子；若产品希望完整统计，在任务 #2 或独立缺陷中补齐各登录方式更新时间。

**验收**：同一用户多次登录不重复计数；每个日期组 active_users ≤ new_users；说明或验证密码登录覆盖情况。

### S09 · P2：服务费表单未冻结精度，合法 UI 输入可能被后端拒绝

**位置**：`modules/06-system-config.md` §3；`api-integration.md` §11。

`internal/service/admin_fee.go` 只接受最多两位小数的普通十进制字符串：fee_rate≤100、min_fee≤9999999999.99、split_ratio≤1。UI 雇主百分比若允许 30.5%，转换成 0.305 会被拒绝；前端不能静默四舍五入改变资金分摊。

**建议**：首期雇主百分比明确为 0～100 的整数步进；比例/金额提交统一最多两位小数，最小服务费明确上限，禁止科学计数法。若需要小数百分比，另立后端精度变更任务。

**验收**：30%→0.30 成功；30.5% 在前端明确拒绝；费率和最低费用覆盖精度、上下界与 payer 切换。

### S10 · P2：任务优先级、估时和迁移链接没有同步完成

**位置**：`development-plan.md` §2–4；`admin-backend-supplement-tasks.md` 头部与排期。

- 后端任务头部说 #1～#5 全 P0、其余 P1，但 #2 是二期，#6a/#8 又是 P0，与具体条目冲突。
- Phase 0～7 标注天数合计 8 天，总排期前端实现写 7 天。需统一估算和所包含范围。
- 后端任务单两条来源链接仍指向已移走的 `sxdg-manage/docs/review/`；相对路径检查确认不存在，应改为 `sxdg-manage/docs/prd/review/`。
- 生产反向代理与 SPA 回退被放到二期。若首期仅本地联调，应写明；若首期包含上线，应在首期部署验收中落实，否则深链接和上传代理仍无交付合同。

**建议**：以拆分后的任务 ID 建一份统一依赖表，避免整项“二期”覆盖 P0 子项；同步总排期，修复链接，区分本地联调完成和可部署交付。

**验收**：各文档任务优先级一致；估时可加总；本地链接全部存在；首期部署范围明确。
