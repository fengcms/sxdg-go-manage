## U01（P1）：CLI 运维留痕载体 → 采纳「独立运维日志」

**问题确认**：第三轮裁决要求「adminId 空 + 来源标记 system/bootstrap」，但 `admin_audit_logs.admin_id` 为 BIGINT NOT NULL 且引用 users(id)（schema.md:902、001_init.sql:724、模型 AdminID int64），直接写入必然违反约束——原裁决未交代载体，是我的疏漏。

**裁决（按评审建议，最小改动）**：
- CLI 初始化留痕 = **独立的结构化运维日志**（持久化收集的 JSON 日志），记录：`source: system/bootstrap`、执行时间、目标账号 ID/角色、执行结果；**actor 可空**；**不记录密码、令牌、密码哈希**
- `admin_audit_logs` 保持现有模型与约束**不变**；HTTP 管理写操作继续在业务事务内写审计
- 交付总则第 3 条限定为「**HTTP 管理写操作**全部落 admin_audit_logs」，明确排除无登录 actor 的 CLI；禁止开发时强塞 0 或伪造管理员账号
- 若未来需要把运维留痕纳入后台审计查询界面，另立持久化方案 + 表迁移，**走基线变更裁决**，本轮不放宽审计表约束
- 批次 A 的 #6a 角色初始化保持现有命令行为（输出明确执行结果），首批不改审计表

**验收**：首无管理员时命令仍可执行；运维记录可追溯且不含凭据；失败不记录成功；已有 HTTP 审计不受影响。

## U02（P2）：日期筛选区间精度 → 采纳「半开区间」

**问题确认**：`created_at` 为 TIMESTAMPTZ（微秒精度），冻结的 `[start 00:00:00, end 23:59:59]` 会遗漏 `23:59:59.500000` 等属于结束日的数据。

**裁决（按评审建议）**：
- 日期参数仍按**上海时区**解释；查询合同改为**半开区间**：`created_at >= 起始日00:00:00 AND created_at < 结束日下一日00:00:00`
- 用户语义不变：选择结束日 = 包含该日全部 24 小时
- start/end 顺序错误或日期格式非法 → 参数错误；禁止字符串拼接 SQL
- **验收**：结束日 23:59:59 与 23:59:59.999999 被包含；下一日 00:00:00 被排除；起始边界上海时区转换正确

## 实现细化确认（评审 §4，随裁决一并落入任务单）

- **封禁审计读取**：限定 `targetType=users`、`action=status`、对应 `targetId`，按 createdAt/id 稳定取最新——不得把订单状态动作误当用户封禁记录
- **#6a CLI 角色初始化**：不覆盖已有账号、不提升同名普通用户
