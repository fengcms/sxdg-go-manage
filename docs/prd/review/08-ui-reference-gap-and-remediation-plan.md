# 管理后台参考风格差距分析与整改计划

日期：2026-10-04。状态：待用户评审，本次仅分析与计划，未修改应用代码。

## 1. 结论

当前后台完成了主要业务操作和接口对接，但没有达到参考项目的视觉与交互完成度。需要以参考项目重新对齐设计令牌、工作台布局、基础组件和页面模式，不能只换主色。

这一偏差主要在我：把原风格指导过度当成技术参考，保留了语义变量、统一表单等结构，却自行换了绿色视觉、放大控件和留白，简化了表格、状态标签、导航与弹窗；验收偏重接口和行为，没有建立参考样板与截图对照。44 项单测和 14 项浏览器测试证明已覆盖行为通过，不能证明设计达标。

推荐沿用现有业务层、鉴权、URL 查询、金额和状态约束，以参考项目为视觉与组件规格依据，分阶段整改。不需要重写后端，也不需要把电销业务或其账号体系搬过来。

截图可见的首批问题尤其明确：查询/重置按钮比输入框高一行、导航图标全部相同、正常账号与其他状态缺少语义区分、大量重复描边操作、日期呈英文占位。用户数据大量来自本地测试夹具，昵称重复也会影响观感；这不是增加假姓名就能解决的问题，视觉验收应准备可辨识但独立的测试数据。

## 4. 保留与选择性借鉴

- 保留四角色权限、纯内存令牌、刷新并发控制、会话隔离、证件 Blob、资金精度、固定订单状态动作、客服参与关系和转接失权、未保存确认。
- 保留可分享的详情路由与 URL 筛选。不能为了模仿参考弹窗，把所有详情改为无法直达的临时弹层。
- 参考项目的错误表格使用整页 reload；本项目刷新会丢失内存登录，应继续局部 refetch。
- 参考表格注释提到粘性表头，但已读实现没有 sticky 样式；不能把注释当成已实现证据。本项目需要时单独实现和测试。
- 只移植需要的无业务组件，逐个核对 Radix/Tailwind/React 兼容性；不整体复制 package.json，不引入电销的租户、批量分配、导入等功能。
- 参考站有图表不等于本项目已有同类指标。没有后端口径的数据不画趋势、不补同比、不显示虚构待办数量。
- 主题和侧栏偏好可以单独持久化，令牌与敏感业务缓存仍不持久化。

## 5. 分阶段整改计划

### R0：建立可复查的规格与样板

产出参考组件对应表、设计令牌/尺寸表、页面状态矩阵。确认当前参考与旧指导的差异并留记录。首个样板限定整体布局、用户列表、用户详情摘要及调分/封禁弹窗，包含正常/空/错/加载和长文本。

补参考组件实际渲染对照；参考业务服务不具备运行条件时，用隔离展示页加载其真实组件，仅作视觉标本，明确区分真实业务验收。先形成样板截图供用户检查，再推广全站。这里是推荐的视觉检查点，不是重新讨论已确定的业务规则。

### R1：令牌、布局与基础组件

主要文件：`src/index.css`、`layouts/AdminLayout.tsx`、`config/navigation.ts`、`components/ui/`。

实现蓝灰明暗主题、200/64px 侧栏、56px 顶栏、业务图标、账户菜单、响应式导航；拆分 Button/Input/Select/Badge/Dialog/Dropdown/Tooltip/Skeleton 等组件，完成尺寸、焦点、禁用与错误态。移除或限定全局 table 样式，避免模板预览和嵌套表格互相影响。

验收：1440/1280/1024/390 宽度下导航可达；明暗模式层次清晰；控件不出现原生与自定义混搭；折叠和主题不改变会话行为。

### R2：列表样板与用户模块

主要文件：`components/data/ResourceList.tsx`、`DataTable.tsx`、`feedback/State.tsx`、`pages/Users.tsx`，新增 PageHeader/FilterBar/StatusTag 等。

重构筛选、表格、分页和状态区；用户信息按头像或首字回退、昵称、ID 分层；状态有明确语义；行操作突出查看，其余保持易发现的次级操作，危险项用危险色。查询、重置和展开筛选保留明确动作与 URL 契约。

验收：1440 宽度下普通用户行目标 48～56px（多行内容可例外），筛选按钮与输入基线对齐；长昵称不挤坏操作列；编号/金额对齐；表头与分页策略真实可用；页码不会串到其他列表。

### R3：业务表单与详情重排

主要文件：`feedback/ActionDialog.tsx`、`Details.tsx`、`form/`、用户/资质/交易详情。

约定小确认 420～480px、标准表单 560～640px、复杂编辑 800～960px（均受视口约束），尺寸作为样板起点。详情按摘要、状态、核心字段、关联记录分组；长表单 body 滚动、footer 可见。通用 ActionDialog 保留请求和校验能力，复杂内容可插槽或独立表单，避免继续堆字段配置分支。

验收：封禁/调分/退款清楚展示操作对象、原因、金额和影响；不能因改 UI 丢掉二次确认、输入保留、后端错误或未保存拦截；移动弹窗不超屏。

### R4：逐模块推广

顺序：资质 → 内容 → 订单退款 → 服务需求 → 客服 → 配置审计 → 看板与登录。

- 内容：分类层级与热门排序易辨认；图片预览、模板编辑/预览有独立区域。
- 交易：订单摘要、状态动作、金额、结算与退款来源分组，禁止所有字段同等强调。
- 客服：会话列表/消息区各自明确滚动与选中态，保留参与关系提示，无发送功能伪入口。
- 配置：按用途分组，旧值/新值/生效说明就近显示；审计先中文摘要后可展开原始明细。
- 看板：真实指标卡和现有分布呈现，技术说明改为简明业务口径。登录与整站同一品牌体系。

每个页面逐一核对权限、查询参数、写入确认和空错态。不要只改通用组件后就宣布全站整改完成。

### R5：视觉和业务双重验收

按样板同视口、同数据对比截图；覆盖亮暗、长文本、空数据、加载失败、禁用、焦点、弹窗错误、移动端。金额等动态区域遮罩后建立稳定截图基线；截图差异须人工查看，不能自动更新基线掩盖问题。

执行 `pnpm check`，保留并调整既有 44 项单测和 14 项浏览器场景，按新控件新增主题/折叠/页码窗口/日期/键盘等有意义测试。刷新令牌、四角色、客服转接、退款边界、证件鉴权必须回归。

每阶段独立 Conventional Commit，例如 `feat(ui): 对齐参考项目的主题与工作台布局`，详细 body 写变更和验证；决策与踩坑继续写 `docs/dev-log`。

## 6. 完成标准与实施边界

1. 用户列表、详情与弹窗样板先达到参考的视觉体系，再推广其他模块；以实际截图与操作为依据。
2. 全部现有页面使用一致的标题、工具栏、表格、状态、表单和分页规格，不能残留旧绿皮控件。
3. 四角色原有功能和安全约束无回退；窄屏没有整页横向溢出，表格可局部横滚；键盘焦点、弹窗关闭和主操作可达。
4. 不以新增业务功能代替视觉整改；不迁移数据库、不改接口、不复制参考项目认证与业务模型。
5. 交付前后截图、组件规范、测试结果、遗留项和流水账。功能门禁与视觉验收分别记录。

这轮整改没有已知后端阻塞。主要工作量在通用组件和逐页重新组织，而非换色。具体进度应以 R0/R2 样板实际结果修订，不在缺少样板验证时承诺整站只需几个小时。
